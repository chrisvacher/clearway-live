# Engagement setup

Setup implements SET-01, SET-02, SET-03 and SET-09. `/setup` is the facilitator home, listing RLS-visible engagements with upcoming events first and direct links to their workspaces. `/control` redirects there. Admins create an engagement by choosing an existing Team Hub client and engagement. Both ids are checked by the restricted server reader, including the engagement's client association. Linked engagements already in Live are marked with a link to their setup, and duplicate creation returns a conflict. Existing engagements remain editable while the reader is unconfigured. Fictional seed engagements deliberately have no external ids.

The church, engagement, lead and co-facilitator save in one database transaction. An assigned facilitator can edit church details and their engagement, including a co-facilitator, but cannot change external links or the lead. Admins manage Clearway users at `/setup/users`, explicitly adding approved Team Hub team members with `@clearway.co` email, without granting admin status. No user is automatically admitted just because they exist in Team Hub.

Create and edit show fields by engagement type. Team workshops show a workshop date and optional end date. Wayfinding shows pre-call time, retreat dates, base year, Five Lenses, governance body and Scripture translation. Hidden values are retained when type changes. Pre-call times use the church's IANA time zone and are stored as instants. Ambiguous or nonexistent daylight-saving times require another local time. Retreat dates remain dates. A blank base year uses the retreat year, then engagement start year. A supplied year is preserved, and the 10-year Future, 3-year Vision and 1-year Outlook use it.

Settings control AI permission, Scripture translation, TV theme, texture and room size. Very small screen is the PRD room-size default. Navy/dark is the approved default theme and remains editable. SET-09 is required, editable consensus wording, shown on the phone welcome and in each invitation. Open joining is an admin-only, team-workshop-only setting, off by default. It allows name-only joining by room code, with **Joined by name** shown for guests. See [room sign-in](room-sign-in.md).

**Details** (`/setup/[id]/details`, design pass 8) is four cards: The event (Event title, Kind of event, status, dates and facilitators), The church (logo, Name on screens, time zone), AI in the room, and Wayfinding settings (every kind except a workshop). Each card has its own Save, and every Save sends the whole form through the same `save` action, so a change in another card is saved too. The Team Hub line shows the church and engagement names, never their ids. Time zone is a select of IANA zones (`lib/setup/timezones.ts`). The logo is uploaded with `POST /api/setup/logo`, which checks the origin and the facilitator, checks the type by its bytes (PNG, JPEG or WebP) and the size (1 MB), and writes with the service role to the public Storage bucket `church-logos` (migration `20261113100000_church_logos.sql`). The church's `logo_url` holds the public address, so the TV and join pages read it as before. An address can also be pasted; `lib/setup/policy.ts` accepts an `http` address only on 127.0.0.1 or localhost, for the local kits. Logos are not in the engagement JSON archive or the file protection backups, and a replaced or removed logo's file stays in the bucket.

**Screens** (`/setup/[id]/tv`, called Pair a TV before design pass 8) pairs and names TVs and holds the display settings: Room size (the same option words as the live room), TV theme, the texture and reduced motion. Each message shows beside the button that caused it.

# People and email

Imports show a review before saving. CSV supports UTF-8 BOM, quoted commas, doubled quotes and quoted newlines, with a 128 KB input limit and 500 people per import. Name and email are required. `role` means role at the church. Optional `room_role` explicitly sets participant or scribe. Other fields are retained. Email matching trims and lowercases, keeping the first duplicate. Existing scribe roles stay unchanged when room_role is absent. Pasted lists use `Name <email@example.org>` per line. Team Hub imports resolve the church's persisted link after an RLS check and verify every selected person against that church's current people.

Editing an email or removing a person revokes their existing device access through the existing identity-change trigger. Bulk imports are atomic. Browser input cannot set an Auth identity, verification time, or device binding.
Removing a person goes through `public.remove_attendee(p_engagement, p_attendee)` (migration `20261109040000_overnight_setup_reset.sql`), a security definer function that checks the admin, lead or co-facilitator role, so the lead and co-facilitator can remove people as well as an admin. A plain update to `deleted` is refused for a non-admin by the attendees read rule. Removing a person who is already removed is not an error.

What the page says when a save is refused: `lib/setup/errors.ts` passes the sentence the database raises on purpose (for example "Wait a few minutes before sending more invites." with status 429, and "Review a new invite batch after changing the attendee list." with 409), names a duplicate email ("Someone in this engagement already has that email address.", 409), and gives a 403 line for a role refusal. A raw database error (a table, constraint or policy name) is never shown: the page says "We couldn’t finish that. Check the connection and try again." Saving with the consensus wording empty is refused before it reaches the database: "Explain how the room decides before saving." Unit tests: `tests/unit/overnight-setup-reset.test.ts`; role test: `engagement_setup.test.sql`.

Invites are reviewed and sent in batches of up to 50 through Resend's batch API. A private forced-RLS outbox snapshots recipients, church, dates and consensus. The reviewed batch id is the provider idempotency key, and retries reuse the exact payload for up to 23 hours, within the provider's 24-hour window. Accepted batches are marked sent through a service-only invoker RPC. If marking fails after provider acceptance, retrying uses the same idempotency key. Closing the engagement, removing a recipient, or changing their email blocks a pending batch. Three new batches per engagement per five minutes limit accidental repeats. No automatic retries, background sending, or real-person test emails run in CI.

# Validation

Unit tests cover CSV edge cases, duplicate matching, roles, local times, dates and invitation content. HTTP tests exercise guarded setup routes, import review/save and invite review/send/retry against local Auth, REST and Resend fixtures. PostgreSQL tests prove participants and other-engagement facilitators cannot save setup, import people or queue invitations. They also cover immutable external links, private outbox access, atomic imports, preserved scribe roles, consensus snapshots and admin creation.

**Overnight acceptance fix (November 9).** The invite email writes the retreat dates as the app does ("November 3 to 4, 2026"), not as ISO dates.

# One laptop

Many engagements run from one MacBook Pro: the control surface in one window, the TV as a second window moved to the room's screen. The live room (`/control/[id]`) has its own layout with no sidebar, so it carries what the sidebar would:

- **Back to the engagement** (Overview) above its title.
- **Identity line** under the title: the room link at the engagement's address (`roomOrigin(skin)`), the room code, the brand (Clearway or Novetera) and "N in the room", which jumps to the "At the door" panel on the same page. The PRD puts the door list on the control surface, so it does not leave for the Door list page. Facilitator screens stay Clearway Live whatever the brand.
- **Below 900 px** the order is the live controls, the TV preview, then the rest; the run of show folds behind "Show the run of show". At 1512 px the three columns are unchanged.
- **Open the remote** opens a panel with the remote's link, Copy link, a QR code and "Open it on this computer". The remote needs a Clearway Google account that is an admin or the lead or co-facilitator on Details (`show_allowed` in the database); the link is on the address the window is signed in at.
- **End the workshop** (workshops only, on Results and beside See results in the live room) asks first, then sets the engagement status to closed through the same `save_engagement` function Details uses (`end_workshop` in `/api/setup` rebuilds the Details form with the status changed). Closing signs out every phone and closes answers; results stay. Wayfinding keeps "Mark the retreat closed".
